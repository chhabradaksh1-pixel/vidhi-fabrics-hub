## 1. The loom video is 69% of the page — owner-side

`/weaving-loom.mp4` is 6,059,529 bytes, `autoplay loop muted playsinline`,
with **no `poster` and no `preload`**. It renders in a strip 192 px tall on a
phone. Autoplay makes browsers fetch it eagerly regardless of any preload
hint, so a first-time mobile visitor pays 5.78 MB to fill a 192 px band.

Two corrections to what `CLAUDE.md` currently records:

- The open item says it "revalidates on every visit". Measured: it does
  revalidate, but it returns **304 with 0 bytes**. Repeat visits cost one round
  trip, not 6 MB. The 6 MB is a **first-visit** cost. Still worth fixing —
  playback cannot begin until the revalidation returns — but it is a smaller
  bug than the note implies.
- The reason is now precise. The build emits `.output/public/_headers`
  containing exactly one rule, `/assets/* → max-age=31536000, immutable`.
  Files in `public/` are not covered, so they fall back to Vercel's
  `max-age=0, must-revalidate`. The `?v=a787f8f` on the video was someone
  reaching for fingerprinted caching, and `max-age=0` defeats it.

I did not attempt either fix. Re-encoding needs ffmpeg, which is not available
here. Extending `_headers` means configuring nitro through
`@lovable.dev/vite-tanstack-config`, whose own comment warns against adding to
it manually, and I cannot verify a deployed header from this machine. Both are
escalations under `CLAUDE.md`.

**What would actually fix it**, in order of effect:

1. Re-encode to H.264 at the size it is displayed. A 192–320 px tall loop has
   no use for whatever resolution this is. A few hundred KB is a realistic
   target against 5.78 MB. The camera originals are now in `media-originals/`.
2. Add a `poster` frame, so the band shows something during the download
   instead of nothing.
3. Give `public/` video a long `max-age` with `immutable`, keeping the `?v=`
   convention for cache busting.

## 2. Journal images were 1.5–2.5× oversized — fixed in the PR

Measured in Chrome with every lazy image forced to load, at 390×844 dpr 3 and
1440×900 dpr 2:

| file | intrinsic | renders | over (desktop 2×) |
|---|---|---|---:|
| swatch-on-card | 1800×1200 | 356×267 | 2.53× |
| woven-detail | 1600×1067 | 356×267 | 2.25× |
| spec-samples | 1440×957 | 356×267 | 2.02× |
| warehouse-surat | 1440×900 | 356×267 | 2.02× |
| swatch-stack | 1440×900 | 356×267 | 2.02× |
| swatch-book | 1600×1067 | 545×341 | 1.47× |

Each sits in an `aspect-[4/3]` box (`16/10` for swatch-book) under
`object-cover` with the default centre position, so the browser was already
cropping to that ratio. Doing the crop on disk is appearance-neutral by
construction. Now 1024×768 WebP at quality 82: **1,691,133 → 976,986 bytes,
697 KB off both home routes.**

This also makes the `width`/`height` attributes true. `JournalCard` hardcodes
`width={1024} height={768}` for every card and six of the seven files did not
match. CLS was never affected — the CSS aspect-ratio governs the box — so this
is correctness of metadata, not a fixed layout bug. Saying so because it would
be easy to claim a CLS win here that the numbers do not support.

Honest framing: these images are all lazy-loaded and none is the LCP, so 697
KB does not move a Core Web Vital directly. It is bandwidth for a mobile
audience, and it stops competing with the video for it. **It does not fix this
page. The video does.**

## 3. One image is under-resolved, going the other way

`fabric-katan-jacquard.jpg` is 1024×768 but renders in an `aspect-[4/5]` box at
448×560 on desktop, needing roughly 1493 px of width to cover at 2× — it has
**0.69×** of what it needs and will look soft on a retina display. Fixing it
means a *bigger* file on the story block. Left alone deliberately: it is a
quality call that trades against the payload work above, and it is the owner's.

## 4. Three files in `public/` were served as junk — fixed in the PR

Vercel does not resolve Git LFS, so each was delivered as pointer text under a
video MIME type:

- `/automated-printing-machine-...mov` — 134 bytes, `video/quicktime`
- `/weaving-blue-fabric-on-a-traditional-wooden-loom-...mov` — 134 bytes
- `/From Klickpin.com- Smart clean car habits...mp4` — 131 bytes, `video/mp4`

`CLAUDE.md` knew about the third. There were three. None is linked or in the
sitemap, so the SEO effect is close to nil — this is deploy hygiene, and it is
listed here as such rather than dressed up.

The two `.mov` files are the originals behind the loom video, so they moved to
`media-originals/` instead of being deleted; they are the source material for
the re-encode item 1 asks for. The Pinterest download is unrelated to this
business and is gone. A side effect: a fresh clone no longer pulls ~1 GB of
LFS objects to build the site.
